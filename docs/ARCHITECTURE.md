# معماری همراه

## مرزهای مسئولیت

رابط کاربر فقط درخواست و تصمیم انسانی را می‌فرستد. هیچ کلید لیارا یا Cursor، shell یا API مخرب در مرورگر قرار ندارد. API سمت سرور مرجع وضعیت و اجرای عملیات است.

Worker در هر نوبت، endpoint سلامت و یک endpoint امن بررسی مسیر کسب‌وکار را می‌خواند. شکست‌های پیاپی یک رخداد می‌سازند. قفل probe، شمارندهٔ شکست، تشخیص رخداد فعال و latch اختلال از بررسی هم‌پوشان و ساخت رخدادهای تکراری جلوگیری می‌کنند. latch با مشاهدهٔ سلامت یا شروع سناریوی جدید دمو آزاد می‌شود.

در demo، علت‌یابی فقط از پیام خطای مشخص در لاگ واقعی فروشگاه محلی استفاده می‌کند. در live، Cursor شواهد را از custom toolها می‌گیرد. نبود کلید، خطای شبکه یا نبود شواهد معتبر به گزارش محدودیت/ارجاع ختم می‌شود، نه اقدام حدسی.

## ابزارها و سطوح دسترسی

| ابزار ایجنت      | اختیار  | رفتار                                            |
| ---------------- | ------- | ------------------------------------------------ |
| `list_apps`      | خواندن  | فهرست واقعی API یا نمای مشخص دمو                 |
| `get_logs`       | خواندن  | لاگ حذف‌شده از اطلاعات محرمانهٔ قابل تشخیص       |
| `get_metrics`    | خواندن  | خروجی واقعی `/metrics/summary` یا منبع مشخص demo |
| `get_memory`     | خواندن  | رخداد، تصمیم، گفتگو و probeهای اخیر              |
| `request_action` | پیشنهاد | فقط درخواست تأیید برای restart/backup؛ بدون اجرا |

ایجنت `decide` یا ابزار approve ندارد. فقط مسیر HTTP رابط انسانی به `Engine.decide()` دسترسی دارد. executor برای هر فراخوانی مجدداً مقصد مجاز و قالب پارامترها را بررسی می‌کند. ابزارهای خواندن/پیشنهاد در audit ثبت می‌شوند.

## چرخهٔ تأیید

درخواست شامل نوع عملیات، مقصد، پارامترها، اثر، هزینه، زمان ساخت و انقضاست. SHA-256 نوع، مقصد و پارامترها به تأیید bind می‌شود. تغییر جزئیات، انقضا، رد قبلی یا اجراشدن قبلی مانع dispatch می‌شود. claim وضعیت پیش از اولین await انجام می‌شود تا دو درخواست HTTP در یک فرآیند نتوانند عملیات را دوبار اجرا کنند.

این تضمین تک‌فرآیندی است؛ برای چند replica به transaction/قفل توزیع‌شده و صف durable نیاز است. اگر فرآیند در میانهٔ اجرا بسته شود، هنگام راه‌اندازی عملیات به عنوان ناموفق با نتیجهٔ نامشخص ثبت می‌شود و خودکار replay نمی‌شود.

## بررسی نتیجه

برای اقدام اصلاحی، دو بار متوالی سلامت HTTP و `ok:true` مسیر اصلی باید موفق باشند. مسیر demo یک INSERT واقعی در SQLite و سپس ROLLBACK انجام می‌دهد؛ سفارش آزمایشی را وارد دادهٔ پایدار نمی‌کند. شکست verification رخداد را `ESCALATED` نگه می‌دارد.

برای انتشار live، قبل از بررسی سایت، `currentRelease` باید برابر releaseID همان عملیات شود. سالم‌بودن نسخهٔ قدیمی به عنوان موفقیت نسخهٔ جدید پذیرفته نمی‌شود. حداکثر انتظار این MVP حدود دو دقیقه است؛ پایان مهلت به معنی نامشخص‌بودن/عدم تأیید نتیجه است، نه اثبات لغو انتشار در لیارا.

بازیابی محلی علاوه بر بررسی سایت، محتوای سفارش‌های بازیابی‌شده را با پشتیبان مقایسه می‌کند. تهیهٔ پشتیبان محلی با ذخیرهٔ payload تأیید می‌شود. پشتیبان ابری asynchronous است؛ پذیرش درخواست با آماده‌شدن فایل فرق دارد.

## حافظه

`data/demo/hamrah.sqlite` و `data/live/hamrah.sqlite` داده‌های دو حالت را جدا نگه می‌دارند. SQLite از WAL و busy timeout استفاده می‌کند. collectionهای اصلی `messages`، `incidents`، `actions`، `probes`، `backups` و `releases` هستند. تنظیمات، نیاز کسب‌وکار و payload پشتیبان محلی در `kv` نگهداری می‌شوند.

`data/cursor/` حافظهٔ رسمی JSONL ایجنت و `cursorAgentId` در KV امکان resume را فراهم می‌کنند. `data/agent-workspace` یک فضای خالی جداست؛ فایل کلیدها داخل workspace ایجنت نیست و ابزار خواندن فایل نیز داده نمی‌شود.

audit یک زنجیرهٔ SHA-256 از payload هر رویداد و هش قبلی دارد. خروجی audit صحت کل زنجیره را بررسی می‌کند. آخرین ۳۰۰ رخداد در رابط نمایش داده می‌شود. probeها به ۱۰٬۰۸۰ نمونه محدود می‌شوند. گفتگوها و تصمیم‌ها در DB باقی می‌مانند؛ رابط ۳۰۰ پیام اخیر را می‌گیرد.

## شبکه و احراز هویت

سرور پیش‌فرض فقط localhost است. برای bind خارجی گذرواژهٔ حداقل ۲۰ کاراکتری اجباری است. درخواست‌های تغییردهنده به هدر اختصاصی و Origin معتبر نیاز دارند. CORS عمومی فعال نیست. JSON body محدود است؛ rate limit روی API و chat وجود دارد. Redirect شبکه برای ابزارها و probeها پذیرفته نمی‌شود. URL بررسی فقط از env مدیر می‌آید؛ مدل نمی‌تواند URL دلخواه به fetch بدهد.

این MVP single tenant است. RBAC چندکاربره، session مدیریت‌شده، secret manager، صف چندسروری و پشتیبان خودکار از حافظهٔ خود مدیر هنوز لازم‌اند تا محصول برای استقرار وسیع آماده شود.

# دریافت پروژهٔ واقعی

`Projects` ورودی GitHub یا ZIP را به یک snapshot محلی تبدیل می‌کند. دریافت ZIP با ورودی‌های lazy و سقف اندازه انجام می‌شود؛ هیچ npm install، build، Docker یا کد کاربر روی میزبان تحلیل اجرا نمی‌شود. آرشیو اصلی نگه داشته نمی‌شود؛ فایل‌های شناخته‌شدهٔ محرمانه حذف و فقط سورس قابل‌انتشار در `data/<mode>/projects/<uuid>/source` نگه داشته می‌شود. گزارش و هش فایل‌ها در SQLite ذخیره می‌شوند.

تحلیل ایستا از manifestها، Dockerfile و نشانه‌های کد استفاده می‌کند؛ نتیجه شامل شواهد، ابهام‌ها و موانع انتشار است. در صورت اتصال Cursor، فقط گزارش پالایش‌شده برای توضیح تکمیلی ارسال می‌شود. ابزار `get_project_analysis` همین گزارش را به گفتگو متصل می‌کند؛ متن repository به عنوان دستور اجرا نمی‌شود.

تأیید به شناسهٔ پروژه، هش، پلتفرم، پورت و مقصد متصل است. انتشار زنده از بستهٔ واقعی همین snapshot استفاده می‌کند؛ نمونهٔ گل‌بازار جایگزین آن نمی‌شود. حالت دمو فقط بسته را آماده می‌کند و با بررسی فروشگاه نامرتبط، سلامت پروژهٔ واردشده را تأیید نمی‌کند.
