# مراقبت از گل‌بازار

این جریان برای فروشنده‌ای طراحی شده که می‌خواهد بداند «مشتری می‌تواند سفارش بدهد؟». داشبورد به‌جای نمودار منابع، وضعیت سفارش‌گیری، تصمیم بعدی، پشتیبان و انتشار را نشان می‌دهد. ابزارهای فنی در «ابزارهای بیشتر» باقی مانده‌اند.

## مسیر کاربر

1. پروژه را از GitHub یا ZIP وارد می‌کند؛ تحلیل کد، ساخت برنامه و دیتابیس، اتصال تنظیمات و دامنه در جریان راه‌اندازی موجود انجام می‌شود.
2. همراه، بازبودن سایت و **نوشتن، خواندن و rollback سفارش آزمایشی** را جداگانه بررسی می‌کند. این بررسی پرداخت واقعی انجام نمی‌دهد و سفارش آزمایشی باقی نمی‌گذارد.
3. شکست‌های پیاپی بدون گفتگو رخداد می‌سازند. شواهد جمع می‌شوند؛ پیشنهاد تغییر منتظر تأیید می‌ماند. در اتصال واقعی، تحلیل از Cursor SDK و ابزارهای محدود استفاده می‌کند؛ تشخیص دمو قواعد مشخص برای خرابی‌های کنترل‌شده دارد.
4. تأیید به حساب، تیم، برنامه، دیتابیس، پارامترها و نسخهٔ مشخص کد متصل است. تأیید تکراری، منقضی یا دستکاری‌شده اجرا نمی‌شود.
5. انتشار پس از آماده‌شدن نسخهٔ ایمنی آغاز می‌شود. در لیارا، شناسهٔ همان انتشار باید فعال شود و دو بررسی پیاپی سلامت سایت و سفارش‌گیری موفق باشند. شکست، موفقیت گزارش نمی‌شود و تغییر بعدی تأیید تازه می‌خواهد.
6. بازیابی، شمار سفارش‌های فعلی، نسخهٔ انتخابی، حذف‌شونده و جایگزین‌شونده را نشان می‌دهد. پیش‌نمایش پنج دقیقه اعتبار دارد. پیش از بازیابی نسخهٔ ایمنی تهیه می‌شود؛ تغییر سفارش‌ها بعد از پیش‌نمایش، بازیابی را در تراکنش متوقف می‌کند.

## پشتیبان و قرارداد بازیابی

`server/recovery.ts` نسخه‌های سفارش‌ها را با AES-256-GCM در vault محلی ذخیره می‌کند. checksum از سفارش‌های مرتب‌شده گرفته می‌شود. پیش از ثبت وضعیت «ذخیره و آزمایش شد»، داده در جدول موقت جداگانه درج و بازخوانی می‌شود و نسخهٔ رمز‌شده دوباره خوانده می‌شود. محتوا در گفتگو، snapshot داشبورد یا SQLite مدیر ذخیره نمی‌شود. این آزمایش، تست سازگاری داده است؛ بازیابی کامل زیرساخت یا رزمایش خرابی دیتاسنتر نیست.

فروشگاه SQLite محلی و نمونهٔ PostgreSQL دارای قرارداد خصوصی زیر هستند:

| مسیر | کار |
|---|---|
| `GET /control/backup` | snapshot سازگار سفارش‌ها |
| `POST /control/restore-preview` | درج و بازخوانی نسخه در جدول موقت؛ بدون تغییر سفارش‌ها |
| `POST /control/restore` | مقایسهٔ `expectedCurrentHash` و جایگزینی تراکنشی سفارش‌ها |

در PostgreSQL، جدول سفارش‌ها بین مقایسه و جایگزینی قفل می‌شود. در SQLite از `BEGIN IMMEDIATE` استفاده می‌شود. شناسه‌ها، زمان‌ها، تعداد و اندازهٔ رکوردها بررسی می‌شوند. نتیجهٔ بازیابی با نسخه تطبیق داده می‌شود و سپس تست سفارش‌گیری انجام می‌شود.

این قرارداد **متعلق به برنامهٔ نمونهٔ خودمان است، نه API فرضی لیارا**. کنترل ابری به HTTPS، برنامهٔ دارای مجوز، و کلید حداقل ۳۲ کاراکتری در vault همان حساب و برنامه نیاز دارد. در راه‌اندازی، `HAMRAH_CONTROL_TOKEN` یا `TEST_CONTROL_TOKEN` موردنیاز نمونه خودکار با مقدار تصادفی ساخته و به env برنامه متصل می‌شود؛ کاربر فایل env را ویرایش نمی‌کند.

برای برنامه‌ای بدون این قرارداد، پشتیبان native لیارا از endpoint مستند `GET/POST /v1/databases/{id}/backups` استفاده می‌کند. پذیرفته‌شدن POST کافی نیست: فایل تازه با حجم مثبت باید در فهرست دیده شود. درخواست مبهم قبل از ارسال ثبت می‌شود؛ تلاش بعدی فقط فهرست را می‌خواند و POST تکرار نمی‌کند. بازیابی native دیتابیس در OpenAPI بررسی‌شده مستند نیست و در UI فعال نمی‌شود. [مرجع رسمی DBaaS](https://github.com/liara-cloud/openapi/blob/main/spec/dbaas.yaml)

## پشتیبان زمان‌بندی‌شده

پیش‌فرض خاموش است. کاربر به فاصلهٔ شش ساعت، حداکثر ۲۸ نوبت، نگهداری بدون حذف خودکار و هزینهٔ احتمالی تعرفهٔ حساب رضایت می‌دهد. Worker مستقل از گفتگو کار می‌کند و قفل مشترک با تغییرات دارد. زمان‌بندی و شمار نوبت‌ها در SQLite و به تفکیک حساب ذخیره می‌شوند. در شکست، زمان‌بندی متوقف و خطا نمایش داده می‌شود؛ نوشتن نامطمئن در حلقه تکرار نمی‌شود. پس از قطع برنامه، Worker فقط هنگام اجرای دوبارهٔ سرور کار می‌کند.

## صداقت وضعیت و محدودهٔ آزمون

- پایش متوقف، قطع ارتباط یا شواهد قدیمی وضعیت سالم نمی‌سازند. دادهٔ پایش به حساب متصل است.
- نمونهٔ محلی سفارش‌های واقعی در SQLite دارد. انتشار نمونه در دمو، آزمایش گردش کار است و کد اجراشدهٔ فروشگاه را جایگزین نمی‌کند؛ پروژهٔ آپلودشده هم در دمو فقط بسته‌بندی می‌شود. انتشار واقعی از API لیارا انجام می‌شود.
- قرارداد بازیابی فقط جدول سفارش‌های همین نمونه را پوشش می‌دهد؛ شامل پرداخت، فایل‌های محصول یا اطلاعات سایر جدول‌های یک فروشگاه دلخواه نیست. حداکثر ۱۰هزار سفارش و چهار مگابایت؛ آرشیو و بازیابی عمومی دیتابیس نیست.
- نسخه‌های سفارش‌ها روی همان لپ‌تاپ‌اند. برای حفاظت در برابر خرابی دستگاه، نگهداری مستقل و حفاظت از master key لازم است؛ این نسخه ادعای disaster recovery کامل ندارد.
- آزمون این تغییر شامل SQLite واقعی، مسیرهای HTTP محلی، fixtureهای API لیارا و قرارداد تراکنشی PostgreSQL است. در این نوبت سرویس ابری هزینه‌دار ساخته نشده و اجرای تازه روی PostgreSQL واقعی لیارا یا Cursor زنده ادعا نمی‌شود.

## اجرای محلی و بررسی

```powershell
npm install
npm run dev
```

تنظیم حالت و کلیدها در خود رابط «تنظیمات و اتصال‌ها» انجام می‌شود. محیط پیش‌نمایش آزمون این تغییر به‌طور جداگانه روی پورت ۳۰۰۵ و فروشگاه آن روی ۳۰۰۶ اجرا شده؛ داده‌های حساب اصلی را تغییر نمی‌دهد.

```powershell
node --import tsx --test --test-concurrency=1 tests/*.test.ts
npm run build
```

تست‌های `care.test.ts` چرخهٔ کشف، تأیید، اصلاح، پشتیبان، پیش‌نمایش، سفارش هم‌زمان، توقف انتشار بدون بکاپ، زمان‌بندی و وضعیت قدیمی را می‌سنجند. `pg-recovery.test.ts` قرارداد SQL و قفل/rollback را با fixture تراکنشی می‌سنجد؛ این fixture جای PostgreSQL واقعی نیست. تست‌های موجود ورود سورس، تأیید هزینه، منابع خصوصی، متغیرهای محرمانه، انتشار مشخص و DNS/SSL نیز اجرا می‌شوند.
